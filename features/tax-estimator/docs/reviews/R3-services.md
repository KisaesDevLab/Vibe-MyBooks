## 1. Major findings

### R3-01 — Estimate cache key omits the caller's tenant set (D1)
`estimate.service.ts:262-273` hashes `scope.firmId`, the IN-SCOPE links/companies, payments and snapshots — but not `scope.allowedTenantIds`, and `g.adjustments` (`:267`) is the unfiltered scenario list. `adjustmentMonths` (`:338-355`) then decides per caller whether a GL-linked adjustment's actuals may be read (`isTenantInScope`, `:340`). Two members of the same firm with different `user_tenant_access` therefore produce the SAME key (`:650-651`) for DIFFERENT results whenever the adjustment's company is not one of the taxpayer's linked companies (`assertGlLink`, `adjustments.service.ts:76-86`, only requires the tenant to be in the WRITER's scope).
Failure scenario (probe P1): firm member A (reaches T1, T2) computes; member B (reaches T1 only) computes the same request → `cached: true`, same hash, adjustment "T2 secret" = `12000` (T2's monthly actuals, run-rated), no `TE_TENANT_NOT_MANAGED` warning. With `refresh: true` B correctly gets `0` and the warning. The Clients-screen contract ("exposes nothing the caller could not already see") is broken through Redis.
Fix: add `tenants: [...scope.allowedTenantIds].sort()` to the hash payload (or hash only the adjustments B may read); also make `estimateCacheKey` include a scope digest so two members never share an entry. Add a test: same firm, two scopes, GL-linked adjustment into an unlinked company → second call `cached: false`.

### R3-02 — Every January Q4 payment is counted in two tax years
`paymentWindow(taxYear)` (`payments.service.ts:72-82`) is `[Jan 1 taxYear, return_due_date]` so the window for year Y is Jan 1 Y → Apr 15 Y+1 and the window for Y+1 starts Jan 1 Y+1: the quarter Jan 1–Apr 15 of Y+1 belongs to both. `readGlPayments` has no per-year attribution and `storedRows` cannot exclude a GL row from a year (only supersede it under the same transaction id).
Failure scenario (probe P3): a 2,500 payment on 2027-01-15 appears in the 2026 ledger (correct, Q4) AND in the 2027 ledger (`in2027: [["2027-01-15","2500.0000","federal"]]`). In Jan–Apr 2027 the engine applies it to the 2027 Q1 installment (`payments.ts:141-152`), so the 2027 Q1 voucher is understated by the entire Q4 payment and no penalty accrues on that amount. Every taxpayer who pays Q4 in January hits this on their next-year estimate.
Fix: attribute GL rows to a year explicitly — e.g. a GL row dated before the current year's first installment due date defaults to the PRIOR year (Q4) unless the memo / a stored pin says otherwise; expose "move to year N" (a stored `gl` row with `taxYear` already models this — add the exclusion side: a stored row for year Y with the same transaction id must remove the GL row from year Y+1's live read). At minimum warn `TE_PAYMENT_YEAR_AMBIGUOUS` for GL rows in the overlap.

### R3-03 — Cache key misses reconciliation state (closed-month rule)
The default range end is the last CLOSED month (`closed-month.service.ts:169-191`, from `reconciliations.status/statement_date`), resolved INSIDE `getTaxBasisPl` — after `inputsHash` was computed. The hash covers GL stamps (bumped only by `journal_lines`/`transactions` triggers, TB6), the config version (estimator/TB config tables), parameters and the day — nothing from `reconciliations`.
Failure scenario (probe P2): estimate with `throughMonth` omitted → `2026-09 / last_complete_month`. CPA completes the June reconciliation → the correct default is `2026-06 / last_closed_month` (shown with `refresh: true`), but the plain call returns `cached: true`, still `2026-09`, until the date changes. Readiness warnings in the result are equally stale. The UI's "live estimate" label is wrong for the rest of the day after closing books.
Fix: include a reconciliation stamp per company in the hash — `(SELECT count(*)||max(updated_at) FROM reconciliations WHERE tenant_id=… AND account_id IN (company's reconcilable accounts))` folded into `loadConfigVersion`, or resolve `chooseThroughMonth` per company in `gather()` and hash the resolved months.

### R3-04 — Fallback-year date parameters are not rolled forward
`getParameters` (`tax-parameters.service.ts:161-197`) serves the latest earlier year's rows verbatim when a year has none, marking them `provisional`/`fallback`. `parameterKeys.ts:175-193` flags `installments.due_dates`, `installments.q4_file_and_pay_date`, `return_due_date`, `farmer.single_due_date`, `farmer.file_by_date`, `holidays` as `rollsWithYear`, but only "create year from prior" rolls them; the fallback path does not.
Failure scenario (probe P3, `window27`): with no 2027 seed the 2027 payment window is `2027-01-01 → 2027-04-15`; the engine's 2027 installments fall due in 2026 (`vouchers.ts:291`), the penalty horizon is 2027-04-15, and every real 2027 payment after April is `TE_PAYMENT_AFTER_RETURN_DUE`. The `TE_PARAMS_FALLBACK_YEAR` warning says "values were used (all provisional)" — a CPA reads that as "rates may be off", not "the calendar is last year's".
Fix: in `getParameters`, when `isFallback`, shift every `rollsWithYear` key by `(year − fallbackYear)` years (reuse the roll-forward used by `createYearFromPrior`), and say so in the warning. Add a test for `return_due_date` under fallback.

### R3-05 — `farmerOverride = false` cannot turn the farmer rules off
`entity-settings` stores `farmer_override BOOLEAN` with NULL = derive; the engine honours `false` (`farmer.ts:237-240`: "does not qualify … the gross-income test was not used"). The service maps it as `farmerOverride: anyOverride ? true : null` (`estimate.service.ts:509, 519`) and still puts every `sch_f` entity in `farmIds` (`:508`).
Failure scenario: Sch F entity with no TB farm codes → provider counts ALL income as farming (`TE_FARM_INCOME_ASSUMED`) → test passes → the CPA sets `farmerOverride = false` to stop it → nothing changes: still `farmer.qualifies = true`, single Jan 15 installment at 66⅔ %, no quarterly vouchers.
Fix: `farmerOverride: anyTrue ? true : anyFalse ? false : null` (and exclude `farmerOverride === false` companies from `farmIds`); with mixed true/false across entities, warn and prefer `false`.

### R3-06 — Standalone PDF: no snapshot, no audit
`pdf.routes.ts:206-217` computes (cache allowed) and streams bytes. MODULE.md "Scenarios, snapshots, standards": "**Finalize** stores an immutable snapshot … when vouchers are issued or a PDF is generated"; PHASES.md Phase 13: "Generating it creates a snapshot. Same renderer as the standalone PDF (D15)"; `estimate-pdf.service.ts:25`: "every PDF the app issues is one [snapshot]". The `reason` enum already has `'pdf'`. The route is also open to `firm_readonly`, which conflicts with snapshot creation being a staff write — a decision is needed, not just code.
Failure scenario: a CPA hands the client a PDF; a week later nothing in `tax_est_snapshots` or `audit_log` records what was issued (figures, parameters with statuses, disclaimer in effect). The §7216 trail MODULE D9 asks for does not exist for the primary deliverable.
Fix: `pdf.routes.ts` → `createSnapshot(reason: 'pdf')` then render from the snapshot payload with `opts.snapshot` set (the renderer already prints provenance); gate the route with `requireTaxEstimatorWrite` or let readonly download the LATEST snapshot only; `auditLog(…, 'download', 'tax_est_snapshot', id, …)`.

## 3. What was checked and passed

**D1 / isolation.** Guard chain order (`tax-estimator.routes.ts:29-40`): `authenticate` → `requireSessionAuth` (API keys/download tokens 403 `SESSION_AUTH_REQUIRED`) → `userType === 'client'` 404 → flag → resource → `resolveTaxEstimatorScope`. `X-Firm-Id` must name a firm the user is in (404 hides non-membership); super admin must name a firm (400 `TE_FIRM_REQUIRED`) and gets the firm's full managed set; `allowedTenantIds` = active assignments ∩ active `user_tenant_access`, computed server-side; nothing reads a tenant list from the request. Every taxpayer-rooted read is `firm_id = scope.firmId` (`year-access.ts`), every scenario/adjustment loader joins to the taxpayer's firm, payments and snapshots carry `firm_id`, Sch AI snapshots carry `firm_id` and are filtered by `isTenantInScope`. Every books read runs `assertEntityInScope` first and loads the company by `(tenant_id, id)`; `glMonthlyActuals` is only reached after `isTenantInScope`; `readGlPayments` skips out-of-scope links before any query; stored payments pointing at an unreachable tenant are dropped with a warning and can only be deleted; link/contact/company-option reads use `tenantInScopeSql`; snapshot `tenant_ids` gate view/compare (404 `TE_TENANT_NOT_MANAGED`) and blank the summary in the list. `validatePaymentTargets` pins payment taxpayers/persons to the caller's firm. Audit rows are written under the caller's active tenant with `firmId` in the data (R1 F16 fixed).

**D9.** `prior_year_*_encrypted` on `tax_est_years` and `tax_est_state_rows`, `payload_encrypted`/`summary_encrypted` on `tax_est_snapshots` (AES-256-GCM, `utils/encryption.ts`); decrypted only in `years.service` (single-year GET + engine load), `state-rows.service` (engine load; the DTO carries only `*Present`), `estimate-snapshots.service` (verified sha256). Audit shapes strip the ciphertext (`years.service.ts:359-362`, `auditShape` in snapshots is metadata only, state-row audits use `toDTO`). Redis: the estimate cache stores `{ enc }` ciphertext (`estimate.service.ts:654-666`; test `estimate-snapshots.integration.test.ts:86` asserts it); the P&L provider cache holds books figures only. `inputsHash` hashes the decrypted year but the digest is not reversible. No prior-year value appears in a log line or an error message (`runEngine` surfaces engine messages — I grepped the engine's `TE_*` throws; none embed amounts). The sweep discovers all six columns (`years-reencrypt.test.ts`, `snapshots-reencrypt.test.ts`) and the trigger lets it through.
Informational (not a finding): `redactForView` nulls the raw inputs but `payload.result` keeps prior-year-derived lines (`safeHarbor.priorYear.amount`, trace rows). This matches the live POST `/estimate` response and is documented at `estimate-snapshots.service.ts:19-20`.
